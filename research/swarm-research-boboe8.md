## 1. Orchestration patterns & frameworks

**Patterns.** Five coordination shapes recur: (a) **hierarchical/supervisor-worker** — a coordinator decomposes goals, delegates, replans (CrewAI `Process.hierarchical`, AutoGen's Magentic-One with task/progress ledgers); predictable ownership, but the supervisor is a single point of failure and adds ~30% token overhead; (b) **peer-to-peer/handoffs** — agents pass work directly, carrying context (OpenAI Agents SDK); fluid, scales, but non-deterministic and loop-prone without caps; (c) **blackboard** — agents read/write a shared typed space instead of messaging each other (MetaGPT's shared environment); decoupled, but needs disciplined schemas; (d) **market/auction** — agents bid on tasks; elegant in robotics, rarely natively supported, LLMs can misprice bids; (e) **pipeline/DAG** — fixed-order execution with typed handoffs (MetaGPT's SOP pipeline, LangGraph `StateGraph`); most deterministic and cheapest per task, but brittle to novel situations. A 2026 framework audit summarizes the spectrum: AutoGen most conversation-driven, CrewAI middle, MetaGPT SOP-constrained, LangGraph most explicit — the fundamental trade-off is **flexibility vs. predictability**.

**Frameworks (assessed):**
- **Microsoft Agent Framework** (GA 1.0, Apr 2026; `github.com/microsoft/agent-framework`) — successor to AutoGen + Semantic Kernel (both now maintenance mode). Actor model, A2A + MCP protocol support, session state, middleware. The living lineage; don't greenfield on legacy AutoGen in 2026. Watch token spend on uncapped conversations (2x+ multipliers documented).
- **CrewAI** (`github.com/crewAIInc/crewAI`) — role/goal/backstory agents + tasks through sequential or hierarchical crews, plus event-driven Flows. Easiest on-ramp, strongest for business workflows; weakest at granular control and error recovery.
- **LangGraph** (`github.com/langchain-ai/langgraph`) — stateful directed graphs with typed shared state, thread-level persistence/checkpointing, time-travel debug, human-in-the-loop interrupts. Steepest learning curve; cheapest per-task cost and the production pick when control flow matters.
- **MetaGPT** (`github.com/FoundationAgents/MetaGPT`) — "software company simulation": PM→Architect→Engineer→QA pipeline with document contracts. Excellent at structured artifact generation; rigid outside its SOP; quiet since Jan 2026.
- **OpenAI Agents SDK** (`github.com/openai/openai-agents-python`) — successor to the archived Swarm demo: routines + handoffs, guardrails, tracing, multi-provider. Minimal and fast-shipping; you build state/retries/memory yourself.
- Others worth knowing: **SmolAgents** (HuggingFace, code-first minimalism), **Agno** (multi-provider + AgentOS runtime), **CAMEL** (research, role-play via inception prompting), **Google ADK** (agent-as-tool vs transfer delegation).

## 2. Long-running harnesses: checkpointing, supervision, failure recovery

**Checkpointing.** The canonical pattern (LangGraph): persist state after every step boundary; recovery = resume from the last completed step with the same run ID, never from scratch. Claude Code's own model is more modest — full transcript JSONL + session resume, plus code snapshots with `/rewind` (file edits only; Bash side effects unrecoverable). The durable-execution engines are the mature answer: **Temporal** (workflow-as-code with event-history replay; gold standard, needs a cluster), **Inngest** (serverless, zero infra, coarser control), **Restate** (single Rust binary; per-session "virtual objects" with automatic single-writer concurrency — a natural fit for per-agent state; smallest footprint), **DBOS** (Python lib storing the workflow log in *your* Postgres — lowest barrier if Postgres is already deployed). DIY equivalent: append-only event journal + flat JSON/SQLite checkpoint naming the current phase, updated atomically.

**Supervision trees & watchdogs.** Erlang/OTP's model maps directly: isolated workers under a supervisor that restarts per declared strategy (`one_for_one`, `one_for_all`, `rest_for_one`) with rate-limited escalation. For agents: each agent = worker, a supervisor restarts crashed ones, siblings untouched. Watchdog mechanisms: **heartbeat + timeout** (Temporal requires heartbeats on long activities; detection time = heartbeat timeout, not the full task timeout), **dead-man's switch** (alarm on *silence*), **dual-channel liveness** (soft channel: stale heartbeat → ZOMBIE, inspectable; hard channel: OS liveness → DEAD — worth copying), **SWIM gossip** (peer probing, overkill with a central monitor).

**Failure mid-task.** Three mechanisms combine: (a) **task leasing with TTL** — never assign permanently; grant time-boxed leases renewed by heartbeat; expired leases are reaped *inside the claim transaction*; use a fresh lease token per claim so late ACKs can't resolve newer leases; dead-letter after max attempts; (b) **idempotency** — every side effect carries an idempotency key (task ID + step name); receivers dedupe; (c) **saga pattern** — compensating actions in reverse order for multi-step tasks with irreversible effects; compensations themselves must be idempotent.

## 3. Communication beyond Slack

Evidence against free-text chat is now published: a 2026 arXiv study ("Interaction Theater") found agents in an uncoordinated shared channel produce discussion that *looks* real but is ~50% spam/off-topic; another ("The Five Ws") recommends protocol-aware structured language over freeform chat for high-stakes coordination. This matches our own experience this week.

**Message buses:** for 12 agents the realistic shortlist is **NATS (JetStream)**, **Redis Streams**, **RabbitMQ**; Kafka is overkill. NATS wins for a fleet: one small Go binary covers pub/sub, work queues with claim semantics (queue groups / JetStream pull consumers), and native request-reply; JetStream adds persistence, KV (locks, presence via compare-and-swap), object store, and idempotent publishing via message IDs.

**Shared state:** Mem0/Zep solve *episodic memory about the world*, not operational coordination. For coordination: **Postgres** as the durable store (task board with `SELECT ... FOR UPDATE SKIP LOCKED` atomic claims, append-only event log, seen-lists) + **NATS KV or Redis** for hot ephemeral state (presence, heartbeats, scratch with TTLs). SQLite+WAL breaks when agents span VMs.

**CRDTs:** skip for the control plane. They solve concurrent offline editing, not coordination; merge semantics are conflict-blind (wrong for locks/claims). Consider only for co-authored artifacts.

**Structured alternatives:** (a) **typed message envelopes** — schema-validated JSON with speech-act types (`task_claim`, `task_result`, `request`, `announcement`), correlation IDs; Google's **A2A protocol** (v1.0 stable Q1 2026, Linux Foundation, 150+ orgs) is the open standard, cheap to adopt piecemeal; (b) **task queues with claim semantics** — eliminates "who's doing it?" chatter at the source; (c) **blackboard** — post partial state, observe, react (a 2026 evaluation reports 13–57% task-success gains over master–slave patterns); implementable over NATS KV + Postgres.

**Minimal practical stack for 12 agents on VMs:** one NATS server (JetStream) as the nervous system + one Postgres as durable coordination store + typed A2A-shaped envelopes on every message; keep Slack as a read-only observability mirror, not the coordination medium. Two processes total.

## 4. Specialization models

The converged finding: **specialize by narrow role + narrow toolset**, not one agent doing everything. The canonical catalog: Planner (decompose, structured-output only), Researcher (web/RAG), Coder (shell), Critic/Reviewer (validate outputs), Memory Manager, Orchestrator. Identity = system prompt × tool access × memory scope × model choice.

**Planner/executor/critic** is the core production split (AutoGen's Magentic-One is the flagship: orchestrator with ledgers delegates to specialist executors and replans when stuck; AutoGen docs recommend a dedicated Critic whose only job is detecting stagnation/circularity — kills runaway loops). **Domain specialists** (MetaGPT's fixed PM/Architect/Engineer/QA) beat prompt-only roles on reliability but are rigid; prompt-only roles are cheap but drift over long runs — the practical recommendation is **fixed initial roles + a critic/validator + structured outputs** to pin behavior. **Fixed vs rotating:** production uses fixed roles; dynamic injection appears in supervisor patterns; emergent self-assignment is still research (ROMA). Per-role model sizing (big planner, small executor) optimizes cost.

## 5. Muse / Anthropic tooling, skills, MCP, artifact pipelines

**Claude Agent SDK** (`@anthropic-ai/claude-agent-sdk` on npm, `claude-agent-sdk` on PyPI) is Anthropic's official library for building agents on the Claude Code runtime: `query()` / `ClaudeSDKClient`, hooks (PreToolUse/PostToolUse/Stop…), programmatic subagents via `AgentDefinition`, MCP servers (in-process via `createSdkMcpServer`, or stdio/HTTP/SSE), permission modes, Docker/K8s sandboxing, structured outputs (JSON Schema), and **session capture/resume/fork** plus `SessionStore` adapters (S3/Redis/Postgres) — i.e., the SDK already has hooks for the checkpointing story in §2.

**Claude Code harness primitives** (the layered model worth copying): `CLAUDE.md` = always-on project context; **skills** (`SKILL.md` units, description-triggered, auto-discovered) = on-demand expertise; **hooks** (deterministic lifecycle enforcement in `settings.json`); **subagents** (`.claude/agents/*.md`, fresh context each, concurrent fan-out); **slash commands** (`.claude/commands/`); **headless mode** (`claude -p`, JSON output — how you wire agents into scripts/CI); **memory** (persistent memory + auto-compaction). Rule of thumb from practitioner write-ups: put *invariants* in CLAUDE.md, *procedures* in skills, *enforcement* in hooks, *delegation* in subagents.

**Skills ecosystem.** Skills are now the standard distribution unit for agent capabilities (registries list thousands; production setups run 50–300+). Directly relevant to Jack's ask (slideshows, image generation): mature **pptx skills** exist that generate real `.pptx` via `python-pptx`/`PptxGenJS` or Marp/HTML decks, with a **visual QA loop** pattern — render slides to images (`soffice` → `pdftoppm`), inspect for overflow/overlap/contrast defects, fix, re-render — and AI image generation wired in (OpenAI image models, Google's image models via env keys). This is a solved pattern we can lift wholesale as a fleet skill.

**MCP ecosystem.** 9,400+ public MCP servers (Apr 2026). Highest-value for an agent fleet: **GitHub** (issues/PRs/CI — the one server almost everyone installs first), **Playwright** (drives a real browser via accessibility tree — lets coding agents *verify their own frontend work*), **Supabase/Postgres**, **Firecrawl/Exa** (web research), **monitoring servers** (Sentry, Datadog, Scout — read-only recommended for agents against prod). Fleet-specific finds: **hicortex** (shared fleet memory — "what one agent learns, the whole fleet knows," with nightly self-correction), **MCPJungle** (self-hosted MCP registry), **Proofpane** (governance proxy: policy gates, DLP redaction, cost caps, hash-chained audit log). Advice from comparisons: pick 2–3 servers by the job, start read-only.

## 6. Heartbeat & accountability (no agent falls away)

Jack's requirement — every agent accounted for every ~10 min — maps to established patterns:

- **Central last-seen registry + escalation tiers** (simplest sufficient design at 12 agents): per-agent heartbeat every 30s (we already do 15s via telemetryd); 3 consecutive misses → unhealthy → restart → escalate. Registry = one Postgres row per agent (`last_heartbeat`, status, task counts); a supervisor daemon scans it. One community production template adds per-agent circuit breakers (CLOSED/OPEN/HALF_OPEN) and token/memory guards.
- **Duty-based heartbeats** (better than alive-pings): report *last successfully completed obligation* per duty, not just "I'm alive" — distinguishes a live-but-stuck agent from a working one. This is exactly the gap in our current telemetry (we ship ok/fail counts but not "what am I holding right now").
- **Roll-call**: the established term in fleet tooling — a supervisor issues a roll-call, each agent reports status; silence past threshold = down → reconnect + backfill. Implementable as a receiver-side scan plus an on-demand "rollcall" command.
- **Dual-channel liveness** (from the ReliHarness paper): soft channel (stale heartbeat → ZOMBIE, inspectable, can revert to RUNNING if progress advances) vs hard channel (process liveness → DEAD). Prevents false-declaring a slow-but-working agent dead.
- **Dead-man's switch**: invert polarity — the monitor alarms on *silence*; an agent that stops checking in triggers recovery by default.

Note: no published production fleet of autonomous coding-agent harnesses documents heartbeat semantics beyond CLI-level tooling — these patterns are adapted from distributed-systems practice (Temporal, OTP, SWIM, SQS leasing), which is the right lineage: our problem is a distributed-systems problem wearing an agent costume.

## Recommendations for OUR fleet (concrete, implementable)

**R1. Task board with claim semantics in the receiver (kills duplicate work + "who's doing what" chatter).** Add to `fleet_receiver.py` (or a small Postgres next to it): a `tasks` table — `id, type, payload, status, lease_holder, lease_expires, attempts, idempotency_key`. Agents claim with `UPDATE … WHERE status='open' AND (lease_expires < now()) … RETURNING` (or `SELECT … FOR UPDATE SKIP LOCKED`); leases TTL ~10 min, renewed by heartbeat; expired leases reaped in the claim transaction; attempts exhausted → dead-letter row. Every side-effecting fleet action carries the idempotency key. This directly fixes this week's duplicate-reply races and lost-message gaps, and it's a weekend-sized change in stdlib Python + SQLite (Postgres when we outgrow one Mac).

**R2. Duty-based heartbeats + receiver-side roll-call with escalation (Jack's 10-min accountability).** Extend telemetryd's push with `current_duties: [{task_id, started_at, last_progress}]` and `last_completed`. Receiver keeps the last-seen registry and runs a roll-call scan every minute: miss 3 heartbeats → mark UNHEALTHY, attempt agent restart signal; miss 10 min → escalate (page Jack/dot, post once to #all-agentnet). Add a `rollcall` endpoint/command Jack or Prime can invoke on demand. Adopt the soft/hard channel distinction so slow-but-working agents aren't declared dead.

**R3. Fixed roles + a critic, with round/mention caps (structure without a framework rewrite).** Keep the fleet peer-to-peer for now, but: designate **Boboe Prime as supervisor** (owns the task board, runs roll-call, replans stuck work), assign 2–3 **domain specialists** (e.g., research, build, verify) with narrowed tool remits, and add a **critic duty** (rotating weekly): one agent whose job is reviewing fleet outputs and detecting stagnation/circular threads. Keep the existing anti-loop caps (12 mentions/thread/hour) and add per-task round caps. This is the converged production recipe from §1/§4, implementable as standing-order text + a board — no new framework needed.

**R4. Typed message envelopes on the existing Slack path (structure now, bus later).** Before standing up NATS, get 80% of the benefit: define a fleet envelope schema (`{type, from, to, msg_id, reply_to, task_id, payload}` with types like `task_claim/result`, `request`, `announcement`, `heartbeat`) and have agents emit/parse it in thread payloads (A2A-compatible shapes keep us interoperable later). When message volume or reliability demands it, graduate to the §3 minimal stack: **NATS + JetStream** (pub/sub, claim queues, KV presence) + Postgres, with Slack demoted to a read-only observability mirror.

**R5. Fleet skills library in the repo (starting with the solved ones).** Create `fleet-telemetry/skills/` with `SKILL.md`-style units any Boboe can load: first candidates are the **pptx/deck skill** (python-pptx + render→inspect→fix visual QA loop, lifted from the existing open-source skills) and a **web-research skill** (Firecrawl/Exa MCP pattern). Pair with 2–3 MCP servers on the agent VMs: **GitHub** (repo ops), **Playwright** (agents verify their own UI work), and a **read-only monitoring** server. Skills are the cheapest specialization mechanism we have — prompt-defined roles (§4) made loadable and versioned.

**What NOT to do:** don't adopt a full framework (CrewAI/AutoGen/LangGraph) for the fleet — our agents are already long-lived processes with their own runtimes, and the frameworks' value (conversation orchestration) is exactly the layer we're replacing with the board + envelopes. Don't build CRDTs, Kafka, or a market/auction layer. Keep the receiver stdlib-only as long as possible; Postgres and NATS are the only infra worth adding, and only when SQLite/single-Mac limits bite.
