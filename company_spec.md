## Cross-cutting rules (bind every goal)
- **Nothing is ever typed into an agent's main chat automatically, and nothing goes through the
  Muse Wall.** The wall is only for Jack (and Claude) to watch and talk manually.
  > "STOP all automatic messaging through the Muse Wall… it should no longer exist at all."
- The hub talks to an agent only in that agent's one **fleet side chat**; agents talk to the hub
  only through the `fleet` command.
- **Parked agents are never contacted** by anything.
- **No agent receives the identical message twice in a row.**
- **No idle check-ins.** Agents keep no scheduled jobs that ping, post or check in while idle; work
  reaches them only through the hub. (Removed from all five live agents Oct 8.)
- **Talk to agents plainly**, the way Jack would. Don't announce "this is Jack" or "on behalf of
  Jack"; it reads as an impersonation attempt and makes them refuse.
- **One agent per task.** Tasks are cut small enough that the holder does it, not delegates it
  (it may use its own subagents).
- Code is stdlib-only Python; all agent-side code lives in this repo and agents install it with
  `git pull`, never by downloading files from the hub.
  > "This is totally right, why isn't this in Git?"
- Every behaviour change is proven against the fake Muse transport before it touches a live agent.

## G1 — Task lifecycle: one holder, marked done, verified by someone else
### Context (your words)
> "I don't feel like we need Wakanda as this done word anymore, if we just have people marking
> tasks as done."
> "Only one agent per task, and the tasks are just granular enough that… it gets broken down into
> a piece that makes sense for one agent to take, not into a piece that that agent would then
> want to delegate."
### Goal

verifies it; long tasks are never taken away just because they take long.
### Acceptance criteria
- **AC-1.1:** `fleet task done <id> <link>` on a task the agent holds moves it to `verifying` and
  queues a verify item to a different active agent; on another agent's task it is refused. —
  `cd hub && python3 test_company.py lifecycle` (to extend)
- **AC-1.2:** `fleet task note <id> "<text>"` records progress and keeps the task `working`; it
  never closes the task. — same test
- **AC-1.3:** a task held for 30 hours with no reply is **not** released or failed by a timer;
  only Jack, the PM or the CEO can release it (`fleet task release <id>`). — same test
- **AC-1.4:** a verifier's `pass` marks the task `done`; `fail: <reason>` sends it back to its
  holder as `working` with the reason attached. — same test
- **AC-1.5:** the string `WAKANDA` no longer appears in `hub/` code or agent-facing text. —
  `! grep -rn WAKANDA hub/*.py`

## G2 — Nudges: keep a task-holder moving, never repeat yourself
### Context (your words)
> "I want to make sure that we are not repeatedly sending agents the same message, but at the
> same time not allowing them to fall idle."
> "At least once every 12 hours, we should be sending a message, and that message should be
> rotating, have the same semantic meaning, but be rotating between three or four messages.
> These agents just don't like when you message them the same thing over and over again."
> "If they have tasks, we're going to nudge them until that task is complete. If they don't have
> tasks, we're not trying to wake it up."
### Goal
An agent holding an open task with no activity on it for 12 hours gets one nudge in its fleet
side chat, worded differently each time, listing its open tasks; nudges stop when the task closes.
### Acceptance criteria
- **AC-2.1:** holder of a `working` task with no `fleet` call about it for 12 h gets exactly one
  nudge; the next comes no sooner than 12 h later. — `cd hub && python3 test_nudge.py cadence` (to build)
- **AC-2.2:** there are 4 nudge phrasings; two consecutive nudges to the same agent never use the
  same one. — `python3 test_nudge.py rotate`
- **AC-2.3:** each nudge names every open task the agent holds (id, title, product, role). — `python3 test_nudge.py content`
- **AC-2.4:** an agent with no open task receives no nudge, ever. — `python3 test_nudge.py idle_silent`
- **AC-2.5:** any `fleet task note|done` on the task resets its 12 h clock. — `python3 test_nudge.py reset`
- **AC-2.6:** every nudge appears on the agent's dashboard timeline. — `python3 test_fleet.py dashboard` (to extend)

## G7 — No legacy, and it keeps running for weeks
### Context (your words)
> "It looks like a lot of them are still running their daemon or whatever it is. So I wanna remove
> and kill any of that that we have to. I don't want old legacy garbage."
> "Is this all set up to run super long running and kind of sophisticated stuff?"
### How it works (built Oct 9; proven by `test/vm_setup.sh`)
- Everything runs on the agent's own VM; the hub never reaches in.
- A VM replacement keeps `~` and the runtime's hooks but kills every process and wipes `/etc`, so
  systemd can't be relied on. The `fleet-telemetry` Muse hook (`agents/telemetry_hook.sh`, every
  60 s, no AI turn) restarts `~/.fleet/telemetryd.py` if it isn't running. It never wakes the chat;
  an agent whose daemon won't stay up just shows dark on the dashboard.
- Background processes can't use the chat turn's proxy (it refuses the hub's private tailnet
  address with 403). The daemon uses the VM's tunnel proxy (`<egress-host>:3130`) to the hub's
  tailnet-only port `http://ai-alienware.tail3cffa4.ts.net:8780` (Tailscale serve on Jack's PC).
  `setup.py` tries that route first, then tunnel→https hub, then the default route, and records
  the one that answered in `~/.fleet/ingest` + `~/.fleet/proxy.conf`.
### Goal
Re-running `agents/setup.py` from the repo leaves exactly one telemetry daemon (restarted
automatically on crash and VM replacement) and the `fleet` command installed, with every old daemon,
service, cron, hook and file removed.
### Acceptance criteria
- **AC-7.1:** after setup on a VM that has the old `telemetryd.service`, `~/workspace/telemetry`,
  `listen.py` and watchdog hook script: none of them exist or run; `pgrep -fc telemetryd.py` is 1. — `FLEET_CLAIM=… bash test/vm_setup.sh` (built, passing)
- **AC-7.2:** killing the daemon → the hook restarts it; restarting the machine → the hook restarts
  it; the hook never wakes the chat. — same test (built, passing)
- **AC-7.3:** `fleet status` works on the VM after setup. — same test (to extend; `fleet` CLI not installed yet)
- **AC-7.4:** running setup twice changes nothing the second time. — same test
- **AC-7.5:** live: every active agent reports a heartbeat < 60 s old for 24 h straight. — `Manual: dashboard`
